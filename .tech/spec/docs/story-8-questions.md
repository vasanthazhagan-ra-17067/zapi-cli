# Story 8 – Trace System Brainstorm Q&A

> Every Q&A below was generated by examining `story-08.json`, `tech_spec.md`, and the live codebase (ApiClient, Program.cs, ErrorCodes). Items are grouped by theme.
>
> **Revision 2 (2026-03-20):** Three use cases reviewed and incorporated:
> 1. Session assigns a `unique_id` (UUID) on start
> 2. All API request/response details logged except security-related headers
> 3. Default trace export path (configurable) + `--export-path` flag; error if neither set

---

## 1. Architecture & Design

**Q1: Why inject `ITraceWriter` into `ApiClient` rather than `ITraceSession` directly?**  
A: Separation of concerns. `ApiClient` should not know about session lookup, seq increments, or file paths — it just hands off a completed `ApiTraceEntry`. `TraceWriter` owns the complexity of: (1) checking whether a session is active, (2) incrementing the seq counter via the Mutex, and (3) appending to the JSONL file. This also makes `ApiClient` unit-testable via a simple `ITraceWriter` mock.

---

**Q2: Why register `TraceSession` and `TraceWriter` as singletons?**  
A: `sessions.json` state must be consistent across all DI resolutions within a process. Multiple scoped/transient instances could each read stale state and corrupt the index. Singleton guarantees one reader/writer per process lifetime, matching the Mutex-based concurrency design.

---

**Q3: Why use a cross-process named Mutex instead of `lock()` for seq safety?**  
A: An AI agent could fire multiple `zapi-cli` processes in parallel (e.g., parallel API calls). A `lock()` only guards within a single process. The named Mutex `"Global\zapi-cli-trace-<sessionName>"` ensures across-process mutual exclusion so the `entryCount` in `sessions.json` stays accurate and seq numbers are unique.

---

**Q4: Why is the two-interface split (`ITraceSession` + `ITraceWriter`) the right design?**  
A: `ITraceSession` manages session lifecycle (start/close/remove/list/incrementEntryCount) — consumed by command classes and `TraceWriter`. `ITraceWriter` is the narrow write interface (appendApiEntry/appendPexEntry) — consumed only by `ApiClient` and the future `pex drain` command. Consumers of each interface never see more than they need, enabling independent mocking in tests.

---

## 2. Storage Path Discrepancy

**Q5: There is a conflict in the spec. `tech_spec.md §10` shows `<configDir>/zapi-cli/traces/` but `story-08.json contextForAgent` explicitly says `<configDir>/traces/`. Which wins?**  
A: The story's `contextForAgent` is the implementation authority and explicitly calls this out: _"NOT `<configDir>/zapi-cli/traces/` — no extra subdirectory."_ `§8 Storage` table in the tech_spec also shows `<configDir>/traces/sessions.json` (no extra subdir). The correct path is `<configDir>/traces/`. The `§3 Project Structure` example in tech_spec is a documentation error. Implement as: `<configDir>/traces/sessions.json` and `<configDir>/traces/<session-name>/trace.jsonl`.

## 3. BaseUrl Field Discrepancy

**Q6: The JSON example in `tech_spec.md §10` shows `"base_url": "https://desk.zoho.com/api/v1"` (includes path prefix). The story says BaseUrl = `uri.GetLeftPart(UriPartial.Authority)` (scheme+host+port, no path). Which is correct?**  
A: The story's `contextForAgent` is the implementation authority: `uri.GetLeftPart(UriPartial.Authority)` returns only the scheme+host+port (e.g., `"https://desk.zoho.com"`). The path `/api/v1` is part of the `Url` field, not `BaseUrl`. The JSON sample in `§10` appears to be a mistake. Use `UriPartial.Authority` for `BaseUrl`.

## 4. Security

**Q7: Why must Authorization be stripped in `TraceWriter.AppendApiEntryAsync` and NOT in `ApiClient`?**  
A: Defense in depth. `ApiClient` already prevents command classes from injecting an Authorization header. But `ApiClient` is the one that _constructs_ the `ApiTraceEntry` with `RequestHeaders` copied from the outgoing request — and that request includes `Authorization: Zoho-oauthtoken <token>`. If `ApiClient` also stripped it before passing to `TraceWriter`, any future code path that bypasses that strip would silently leak tokens into the JSONL file. Making `TraceWriter` the enforcer means the token can _never_ hit the file, regardless of how the entry was built.

---

**Q8: What is the correct implementation of the case-insensitive Authorization exclusion?**  
A: In `TraceWriter.AppendApiEntryAsync`, before serializing:
```csharp
var safeHeaders = entry.RequestHeaders
    .Where(kv => !kv.Key.Equals("authorization", StringComparison.OrdinalIgnoreCase))
    .ToDictionary(kv => kv.Key, kv => kv.Value);
var safeEntry = entry with { RequestHeaders = safeHeaders };
// serialize safeEntry, not entry
```
The original `entry` object is not mutated (records are immutable).

---

**Q9: Should `ResponseHeaders` also be filtered for sensitive values?**  
A: Story 8 only mandates Authorization exclusion from `RequestHeaders`. Response headers are not filtered in-scope. However, note that some Zoho APIs set `Set-Cookie` or authentication-related response headers — this is a future improvement to consider but is out of scope for this story.

---

## 5. Data Model & Serialization

**Q10: `ApiTraceEntry.Type` is `string Type => "api"` — a computed expression-body property. Will `System.Text.Json` serialize it?**  
A: Yes. `System.Text.Json` serializes all public gettable properties by default. An expression-body property `string Type => "api"` is a public get-accessible property that serializes to `"type": "api"` under `snake_case` naming policy. No `[JsonPropertyName]` annotation is needed.

---

**Q11: Is `Seq` per-session or globally unique across all sessions?**  
A: Per-session. `IncrementEntryCountAsync` increments the `EntryCount` on the specific session entry in `sessions.json` and returns the new count as the seq number. Two different sessions can each have `seq: 1`. Within a single session, seq is monotonically increasing.

---

**Q12: What does `ApiTraceEntry.Error` contain, and when is it non-null?**  
A: `Error` is non-null **only on transport failures** — network errors, connection refused, DNS failures, timeouts (where `HttpClient` throws an exception). It is NOT set for HTTP 4xx/5xx responses, which are normal HTTP traffic. In those cases, `ResponseStatus` contains the status code. `Error` = exception message string (e.g., `"The operation was canceled."`, `"Connection refused."`).

---

**Q13: What should `DurationMs` measure when there is a 401 → refresh → retry?**  
A: The story doesn't explicitly address this, but the most debuggable value is the duration of the **final** HTTP call (the retry after token refresh). A trace reviewer needs to know how long the successful (or failed) call took, not the sum of a failed attempt plus a retry. Capture `Stopwatch.StartNew()` just before the final `SendAsync`, stop after reading the response body.

---

**Q14: Should `sessions.json` use the same `snake_case` JSON serialization policy as `accounts.json`?**  
A: Yes. Consistency across all config files. `TraceSessionEntry` fields like `StartTime`, `EntryCount`, `Status` should serialize as `start_time`, `entry_count`, `status` via `JsonNamingPolicy.SnakeCaseLower`.

---

## 6. Concurrency & Edge Cases

**Q15: What is the exact Mutex acquire/release pattern to use?**  
A:
```csharp
var mutexName = $@"Global\zapi-cli-trace-{sessionName}";
using var mutex = new Mutex(false, mutexName);
bool acquired = false;
try
{
    acquired = mutex.WaitOne(2000);
    if (!acquired)
    {
        _logger.LogWarning("Trace mutex timeout for session '{Session}' — entry dropped.", sessionName);
        return;
    }
    // ... increment entryCount in sessions.json, get seq ...
}
finally
{
    if (acquired) mutex.ReleaseMutex();
}
```
The `Global\` prefix allows cross-process visibility on Windows. On macOS/Linux, `Mutex` with a name also works for cross-process scenarios via named semaphore semantics.

---

**Q16: Can multiple sessions be active simultaneously? Does `StartSessionAsync` deactivate an existing active session?**  
A: The story does not implement "only one active session at a time" logic. The check is: throw if a session with **this name** already exists (regardless of status). Multiple sessions can have `status: "active"` concurrently (they write to separate files). `GetActiveSessionNameAsync` returns the **most recently created** active session, or the only one. If multiple are active, the spec doesn't resolve which to use — this edge case should be documented. Recommendation: return the most recently started active session; emit a `LogWarning` if multiple active sessions exist.

---

**Q17: What happens if `sessions.json` is corrupted (invalid JSON)?**  
A: Catch `JsonException` in any `sessions.json` read and throw `ZapiCliException("sessions index is corrupted", ErrorCodes.IO_ERROR, exitCode: 1)`. Do not silently overwrite a corrupted file — the user's session history should not be silently destroyed.

---

**Q18: What happens if `RemoveSessionAsync` is called but the session directory doesn't exist on disk?**  
A: Handle gracefully. Remove the entry from `sessions.json` regardless of whether the directory exists. Use `Directory.Exists` check before `Directory.Delete`. This covers cases where the user manually deleted the folder.

---

**Q19: What if `trace.jsonl` grows very large (e.g., 100MB from thousands of API calls)?**  
A: Story 8 has no file size limit — single-session JSONL is unbounded in v1. This is a known v1 limitation. Note it as a future improvement: `--max-entries` flag or session rotation.

---

**Q20: What happens when `configDir` doesn't exist on first trace write?**  
A: `TraceWriter` must create the full directory chain: `<configDir>/traces/<session-name>/`. `Directory.CreateDirectory(path)` is safe to call even if the path already exists (idempotent). Always call it before opening the file for append.

---

## 7. Command Design

**Q21: Should `trace session start` fail if a session with any active status already exists, or only if the exact name already exists?**  
A: Only if the **exact name** already exists (regardless of status). If a session named `"my-session"` exists with status `"closed"`, `StartSessionAsync` should still throw. Names are unique identifiers — you can't create two sessions with the same name. Use `RemoveSession` first if you want to reuse a name.

---

**Q22: Can a closed session be reopened?**  
A: No. There is no "reopen" command. `StartSessionAsync` throws if the name already exists in `sessions.json`, so a closed session's name is "taken." Users need to `trace session remove` the old session first, then `trace session start` a new one with the same name, or pick a different name.

---

**Q23: The `--product` flag appears in `tech_spec.md §10` for `session export` but is NOT in the story scope. Is this intentional?**  
A: Yes, intentional. `--product` filtering requires the API Registry (P2 feature, not yet implemented). Story 8 only implements `--name`, `--truncate-body`, and `--type`. The `--product` option should be deferred to the API Registry story.

---

**Q24: Should `ExportSessionCommand` validate that `--type` is one of `"api"` or `"pex"`?**  
A: Yes. In `ExportSessionSettings`, add validation or handle it in `TraceExporter.ExportAsync`. If `typeFilter` is provided but is not `"api"` or `"pex"`, throw `ZapiCliException("--type must be 'api' or 'pex'", ErrorCodes.INVALID_ARGS, 1)`.

---

**Q25: Should `trace session close` fail if the session is already closed?**  
A: Not necessarily — idempotency is friendly for scripted usage. But the spec doesn't address this. Safest behavior: if the session is already `"closed"`, set it to `"closed"` again and return success. No need to throw.

---

## 8. Pre-Call vs. Post-Call Tracing

**Q26: Should `ApiClient` create a trace entry for calls that fail pre-HTTP (e.g., `HOST_NOT_ALLOWED`, `ACCOUNT_DOMAIN_BLOCKED`)?**  
A: No. These exceptions are thrown before any HTTP request is dispatched. There is no `ResponseStatus`, `DurationMs`, or response body to record. Trace entries should only be created for calls where `SendAsync` was actually attempted (even if it threw a `HttpRequestException`).

---

**Q27: Where exactly in `ApiClient.CallAsync` should the trace entry be built and appended?**  
A: After Step 9 (reading response body) for success cases, and in the `catch` block for `HttpRequestException` / `TaskCanceledException` (transport failures). A `try/finally` pattern wrapping `SendAsync` ensures the trace entry is always written:
```csharp
var sw = Stopwatch.StartNew();
string? errorMsg = null;
ApiResponse? response = null;
try { response = await SendAsync(...); }
catch (HttpRequestException ex) { errorMsg = ex.Message; throw; }
finally
{
    sw.Stop();
    var entry = new ApiTraceEntry { DurationMs = (int)sw.ElapsedMilliseconds, Error = errorMsg, ... };
    await _traceWriter.AppendApiEntryAsync(entry, ct).ConfigureAwait(false);
}
```

## 9. Unit Testing Strategy

**Q28: How do you test Authorization exclusion without real API calls?**  
A: Mock `ITraceSession` to return an active session name. Inject a real `TraceWriter` (pointing at a temp directory). Call `AppendApiEntryAsync` with a fake `ApiTraceEntry` that includes `RequestHeaders = { ["Authorization"] = "Zoho-oauthtoken secret", ["Content-Type"] = "application/json" }`. Read the JSONL line back and assert: `"authorization"` key is absent, `"content-type"` key is present.

---

**Q29: How do you test concurrent seq integrity?**  
A: Spin N tasks (e.g., 10) each calling `TraceWriter.AppendApiEntryAsync` concurrently. After `Task.WhenAll`, read `trace.jsonl` and parse each line — assert that all N entries are present and that the `seq` values are unique integers 1..N (no duplicates, no gaps). Also assert `sessions.json` entryCount == N.

---

**Q30: How do you test that export is non-destructive?**  
A: (1) Record file length before export (`FileInfo.Length`). (2) Call `TraceExporter.ExportAsync`. (3) Assert file length is identical. This guards against accidental truncation if the file was ever opened in write/create mode instead of append mode.

---

**Q31: How do you test the `--truncate-body` behavior without corrupting the source file?**  
A: (1) Write a trace entry with a long `ResponseBody` (e.g., 200 chars). (2) Export with `truncateBodyBytes: 50`. (3) Assert exported entry's `response_body` is at most 50 chars. (4) Read `trace.jsonl` directly and assert the original 200-char body is still there verbatim.

---

## 10. Implementation Tips & Gotchas

**Q32: How does `TraceSession` receive `configDir`?**  
A: Like `AccountStore`, accept `configDir` as a constructor parameter. In `Program.cs`, it is already resolved via `EncryptedFileKeychainProvider.GetDefaultConfigDir()`. Pass the same value when registering: `services.AddSingleton<ITraceSession>(sp => new TraceSession(configDir, sp.GetRequiredService<ILogger<TraceSession>>()))`.

---

**Q33: What encoding should JSONL files use?**  
A: UTF-8 without BOM. When using `StreamWriter`, pass `new UTF8Encoding(encoderShouldEmitUTF8Identifier: false)`. `File.AppendAllTextAsync` uses UTF-8 without BOM by default on .NET 10.

---

**Q34: Is `--truncate-body` measured in bytes or characters?**  
A: The field is named `truncateBodyBytes` (int) suggesting byte count intent, but `response_body` and `request_body` are JSON strings (Unicode). In practice, using `string.Substring(0, Math.Min(value, body.Length))` (character-based truncation) is simpler and deterministic. The distinction only matters for multi-byte characters. For ASCII JSON bodies this is equivalent. Recommend character-based truncation and document that behavior.

---

**Q35: What is the correct Spectre.Console.Cli tree structure for `trace session` commands?**  
A: Use nested branches:
```csharp
config.AddBranch("trace", trace =>
{
    trace.AddBranch("session", session =>
    {
        session.AddCommand<StartSessionCommand>("start");
        session.AddCommand<ListSessionsCommand>("list");
        session.AddCommand<ExportSessionCommand>("export");
        session.AddCommand<CloseSessionCommand>("close");
        session.AddCommand<RemoveSessionCommand>("remove");
    });
});
```
This matches the CLI spec `zapi-cli trace session start|list|export|close|remove`.

---

**Q36: Should `IncrementEntryCountAsync` acquire the Mutex AND update `sessions.json`? Or just return the next seq without file I/O?**  
A: It must do both — atomically increment the in-memory `EntryCount` on the session entry AND save it back to `sessions.json` under the Mutex. This is what keeps `entry_count` accurate in the session index. If `TraceWriter` were to handle seq locally without updating `sessions.json`, the `list` command would always show 0 entries.

---

**Q37: The `SESSION_NOT_FOUND` error is used by `TraceExporter`. Which exit code should it use?**  
A: Exit code `1` (general recoverable error), consistent with `ACCOUNT_NOT_FOUND`. Add to `ErrorCodes.cs`:
```csharp
public static readonly string SESSION_NOT_FOUND = "SESSION_NOT_FOUND";
```

---

**Q38: What happens if an API call throws an exception _before_ the response is received (e.g., timeout)? Does a trace entry still get written?**  
A: Yes, if the Mutex-guarded session lookup succeeds. `Error` field is set to the exception message, `ResponseStatus = 0`, `ResponseBody = null`. This is the most valuable trace scenario — the developer can see exactly which call timed out, when, and for which session. Ensure `TraceWriter.AppendApiEntryAsync` never rethrows (catch all, log Warning).

---

## 11. Session UniqueId *(Use Case Addition)*

**Q39: The current spec identifies sessions only by name. Why add a `unique_id` (UUID) field?**  
A: A human-readable name like `"Desk-Analysis-2026-03-20"` can collide (after a remove + recreate) and is not safe for programmatic correlation. A UUID assigned at `StartSessionAsync` time is immutable and collision-proof. It also future-proofs cross-device sync or remote storage where two users could create sessions with the same name.

---

**Q40: Where should `unique_id` be generated and stored?**  
A: Generated in `StartSessionAsync` via `Guid.NewGuid().ToString()` and stored as a field on `TraceSessionEntry`:
```csharp
public sealed record TraceSessionEntry
{
    public required string UniqueId { get; init; }   // ← new
    public required string Name { get; init; }
    public required DateTimeOffset StartTime { get; init; }
    public int EntryCount { get; init; }
    public required string Status { get; init; }
}
```
Serializes to `unique_id` in `sessions.json`.

---

**Q41: Should `ApiTraceEntry` reference the session by `name` or by `unique_id`? Or both?**  
A: Both, for different reasons. `Session` (name) is human-readable when browsing the JSONL file directly. `SessionId` (UUID) allows reliable programmatic correlation — if a session is renamed (not currently possible, but possible future) the UUID still matches. Add `SessionId` to `ApiTraceEntry` alongside `Session`:
```csharp
public required string Session { get; init; }        // name — for human readability
public required string SessionId { get; init; }      // UUID — for programmatic correlation
```
Serializes to `"session": "Desk-Analysis-2026-03-20"` and `"session_id": "c1a2b3..."`.

---

**Q42: What should `trace session start` return for the `unique_id`?**  
A: The start command response should include it:
```json
{ "status": "ok", "data": { "unique_id": "c1a2b3d4-...", "name": "my-session", "start_time": "2026-03-20T10:00:00Z", "status": "active" } }
```
The caller (agent) can capture this UUID for later correlation queries.

---

**Q43: Should `trace session export --name` still accept the name, or the unique_id?**  
A: Accept `--name` (the human-readable identifier) for ergonomics — users and agents know the name they started. Internally `TraceSession` looks up the entry by name. The UUID is exposed in the entry for correlation; it is not used as the primary lookup key in CLI commands.

---

## 12. Security Header Filtering *(Use Case Addition)*

**Q44: The spec only excludes `Authorization` from `RequestHeaders`. What other request headers qualify as "security related"?**  
A: At minimum, the following request headers carry credentials or session tokens and must be excluded from trace entries:

| Header | Why sensitive |
|--------|--------------|
| `Authorization` | Access token (already excluded) |
| `Cookie` | Session cookies — can contain auth tokens |
| `X-Auth-Token` | Common alternative auth header |
| `X-Api-Key` | API key authentication |
| `X-Zoho-Whatsapp-Token` | Zoho-specific webhook auth |

Define a compile-time set in `TraceWriter`:
```csharp
private static readonly HashSet<string> SensitiveRequestHeaders = new(StringComparer.OrdinalIgnoreCase)
{
    "authorization", "cookie", "x-auth-token", "x-api-key"
};
```
Filter any key in this set from `RequestHeaders` before serialization.

---

**Q45: Should response headers also be filtered?**  
A: Yes, for completeness. `Set-Cookie` and `WWW-Authenticate` in response headers can reveal session token patterns or auth challenge schemes. Add response header filtering with a separate set:
```csharp
private static readonly HashSet<string> SensitiveResponseHeaders = new(StringComparer.OrdinalIgnoreCase)
{
    "set-cookie", "www-authenticate"
};
```
Apply when building `ApiTraceEntry.ResponseHeaders` in `ApiClient`, or strip in `TraceWriter` alongside request header filtering.

---

**Q46: Should the sensitive header blocklist be user-configurable or hardcoded?**  
A: Hardcoded compile-time constant for Story 8. Making it configurable introduces a risk: a user or agent could accidentally (or maliciously) remove `authorization` from the blocklist. Defense-in-depth means the authorization exclusion must be unconditional. Future story: allow users to _add_ to the blocklist (never remove from the base set).

---

## 13. Export Path & Default Path *(Use Case Addition)*

**Q47: The current spec writes `trace session export` output to stdout. The new use case requires file-based export with a mandatory path. How does this change the command contract?**  
A: This is a breaking departure from the current spec. Resolution:

- If `--export-path <file>` is given → write the JSON array to that file, output `{ "status": "ok", "path": "<file>", "entry_count": N }` to stdout
- Else if a default export path is configured → write to `<defaultPath>/<session-name>.json`, same stdout confirmation
- Else → throw `ZapiCliException("No export path specified. Set a default with 'zapi-cli trace config set --default-export-path <path>' or use --export-path.", ErrorCodes.INVALID_ARGS, 1)`

This replaces "export dumps JSON array to stdout" with "export writes JSON array to a file and confirms via stdout."

---

**Q48: Where is the default export path stored, and how is it set?**  
A: Store in `<configDir>/trace-config.json`:
```json
{ "default_export_path": "/Users/vasanth/traces" }
```
New `trace config` command group:

| Subcommand | Flags | Description |
|-----------|-------|-------------|
| `set` | `--default-export-path <path>` (req) | Set the default directory for trace exports |
| `show` | — | Show current trace configuration |

`TraceConfigStore` (new class, analogous to `AccountStore`) reads/writes this file. Register as singleton in `Program.cs`.

---

**Q49: Should `--export-path` accept a directory path or a full file path?**  
A: Directory path. The file name is auto-generated as `<session-name>.json`. This prevents accidental overwrites if the same session is exported twice (the directory already exists; the file will be overwritten, which is expected since export is non-destructive on the `.jsonl` source). If the user needs a custom file name, they can specify a full path ending in `.json` — detect via `Path.HasExtension(path)`:
- If path has `.json` extension → treat as a file path, use as-is
- Otherwise → treat as directory, append `/<session-name>.json`

---

**Q50: What if the export directory doesn't exist?**  
A: Create it. Use `Directory.CreateDirectory(exportDir)` before writing. Don't throw — a missing directory is a normal first-run condition, not an error.

---

**Q51: Does this break the "agent captures stdout" agent workflow from tech_spec §10?**  
A: Yes. The current workflow is:
```
zapi-cli trace session export --name "..."
  → agent captures stdout → saves to api-trace.json
```
With file-based export, the agent no longer gets the JSON array on stdout. The agent workflow should be updated to:
```
zapi-cli trace session export --name "..." --export-path ./api-trace.json
  → agent reads ./api-trace.json for analysis
```
OR set a session-scoped default:
```
zapi-cli trace config set --default-export-path ./traces
zapi-cli trace session export --name "..."
  → file written to ./traces/<session-name>.json
  → agent reads that file
```
The tech_spec agent workflow example in §10 needs to be updated to reflect this.

---

**Q52: Should `ExportSessionSettings` be updated and what does the Spectre registration look like?**  
A: Updated settings:
```csharp
public sealed class ExportSessionSettings : GlobalSettings
{
    [CommandOption("--name")] public required string Name { get; init; }
    [CommandOption("--truncate-body")] public int? TruncateBody { get; init; }
    [CommandOption("--type")] public string? Type { get; init; }
    [CommandOption("--export-path")] public string? ExportPath { get; init; }  // ← new
}
```
`trace config` registration alongside `trace session`:
```csharp
config.AddBranch("trace", trace =>
{
    trace.AddBranch("session", session =>
    {
        session.AddCommand<StartSessionCommand>("start");
        session.AddCommand<ListSessionsCommand>("list");
        session.AddCommand<ExportSessionCommand>("export");
        session.AddCommand<CloseSessionCommand>("close");
        session.AddCommand<RemoveSessionCommand>("remove");
    });
    trace.AddBranch("config", cfg =>  // ← new
    {
        cfg.AddCommand<TraceConfigSetCommand>("set");
        cfg.AddCommand<TraceConfigShowCommand>("show");
    });
});
```

---

**Q53: Should `trace config set --default-export-path` validate that the path exists?**  
A: No — validate at export time, not at config-set time. The path may not exist yet when it's configured (e.g., set in a bootstrap script before the directory is created). At export time, create the directory if it doesn't exist (Q50).

---

**Q54: What new error codes are needed for the export path feature?**  
A: Add `EXPORT_PATH_NOT_SET` to `ErrorCodes.cs`:
```csharp
public static readonly string EXPORT_PATH_NOT_SET = "EXPORT_PATH_NOT_SET";
```
Used when neither `--export-path` nor `default_export_path` is configured. The error message: `"No export path specified. Set a default with 'zapi-cli trace config set --default-export-path <path>' or pass --export-path."` Exit code: `1`.

## 14. Session UUID + Live Write + Reopen *(Use Case Revision — 2026-03-20)*

> These Q&As supersede or revise earlier answers where there is a conflict. The three new use cases are: (1) sessions use UUID as primary key, name is non-unique; (2) trace written live to export path at every API call, no deferred export; (3) session close waits for in-flight calls; (4) sessions can be reopened.

---

**Q55: Now that name is non-unique and UUID is the primary key, how do CLI commands resolve a session?**  
A: Commands accept `--id <uuid>` (always unambiguous) or `--name <name>` (convenience shorthand). If `--name` is used and `FindByNameAsync` returns exactly one session → use it. If multiple sessions share that name → throw `SESSION_AMBIGUOUS` (exit 1) listing the matching UUIDs. If zero sessions match → throw `SESSION_NOT_FOUND`. `--id` never has ambiguity — if not found, `SESSION_NOT_FOUND`.

---

**Q56: What does `sessions.json` look like when two sessions share the same name?**  
A:
```json
{
  "sessions": [
    { "unique_id": "aaaa1111-...", "name": "Desk-Analysis", "status": "closed", "export_path": "...", "entry_count": 5, "start_time": "..." },
    { "unique_id": "bbbb2222-...", "name": "Desk-Analysis", "status": "active", "export_path": "...", "entry_count": 2, "start_time": "..." }
  ]
}
```
Both are valid entries. `GetActiveSessionAsync` returns `bbbb2222-...` (the active one). `trace session list` shows both.

---

**Q57: What does `GetActiveSessionAsync` return when multiple sessions are active?**  
A: Return the most recently started `active` session (highest `start_time`). Log a `LogWarning` if more than one active session exists, since only one session can receive traces at a time. This edge case is unlikely in normal usage — a developer would `trace session close` before starting a new one — but should be handled gracefully.

---

**Q58: The trace file is now written live at every API call. Does `trace session export` still make sense?**  
A: Yes, but its purpose shifts from "capture all entries into a file" to "re-read the live file and output filtered/truncated JSON to stdout." An agent that wants to process the trace programmatically can still use `trace session export --id <uuid> --type api` to get a filtered JSON array on stdout. The trace file itself is always up to date at `export_path` — agents can also read it directly.

---

**Q59: What is the exact file path resolution logic for the export file when `trace session start` is called?**  
A:
1. If `--export-path` points to a file (ends in `.json`) → use that exact path
2. If `--export-path` is a directory (no `.json` extension) → resolve to `<path>/<session-name>-<uuid[0..7]>.json`
3. If `--export-path` is omitted → use `DefaultExportPath` from `trace-config.json` as the directory → same naming as #2
4. If neither `--export-path` nor `DefaultExportPath` is set → throw `EXPORT_PATH_NOT_SET` (exit 1)

The resolved path is stored in `TraceSessionEntry.ExportPath` and never changes for the lifetime of the session.

---

**Q60: Is the trace file JSONL (one object per line) or a JSON array?**  
A: The **live file** is JSONL — one JSON object per line, append-only. This is critical: appending a single line does not require reading or rewriting the whole file. `trace session export` reads this JSONL file and emits a JSON array to stdout. The file format on disk is always JSONL; the JSON array is only the stdout projection.

---

**Q61: How does `trace session close` guarantee it captures all in-flight calls?**  
A: Status-based drain. The close sequence is:
1. Acquire Mutex → set `sessions.json` status to `"closing"` → release Mutex
2. Sleep `waitMs` ms (default 5000)
3. Acquire Mutex → set status to `"closed"` → release Mutex

Any `api call` process that acquired the Mutex for its append BEFORE step 1 will complete before close can acquire the Mutex in step 1 → that entry is captured.

Any `api call` that checks the session status AFTER step 1 sees `"closing"` → its entry is silently dropped (not an error — the API call still succeeds).

The `waitMs` window covers any call that reached `TraceWriter.AppendApiEntryAsync` but hasn't yet acquired the Mutex. In practice, API calls complete in milliseconds; a 5-second window is very conservative.

---

**Q62: Should `trace session close` throw an error if there are known in-flight calls at close time?**  
A: No. The close command should always succeed (within the timeout). The design accepts that entries for calls that are still in progress at `t+waitMs` are silently dropped. This is documented in the help text. If exact capture is required, the caller should ensure all API calls have returned before issuing close.

---

**Q63: When a session is reopened, does `entryCount` reset?**  
A: No. `ReopenSessionAsync` only changes the status from `"closed"` to `"active"`. `EntryCount` is not touched. `IncrementEntryCountAsync` reads the current value and increments — seq numbers continue naturally. Example: session had 15 entries when closed; first entry after reopen gets seq 16.

---

**Q64: After reopen, are new entries appended to the same file?**  
A: Yes. `ExportPath` on `TraceSessionEntry` is immutable — it was set at `StartSessionAsync` and never changes. `TraceWriter` always appends to `entry.ExportPath` using `FileMode.Append`. The reopened session appends to the same file, giving a continuous chronological record.

---

**Q65: What happens if `trace session start` is called with a name that already exists?**  
A: Unlike the old design, this is now allowed — names are non-unique. A new session entry with a new UUID is created. Both sessions coexist in `sessions.json`. The old session is unaffected (still accessible by its UUID).

---

**Q66: Should `trace session close` be a no-op if the session is already closed?**  
A: Yes — idempotent. If the session status is already `"closed"`, return success without modifying anything. This is scripting-friendly.

---

**Q67: How does `ApiClient` know which session's `SessionId` and `Session` name to put in the `ApiTraceEntry`?**  
A: `ApiClient` calls `_traceWriter.AppendApiEntryAsync(entry, ct)` and passes a partially-built `ApiTraceEntry` where `Session` and `SessionId` are populated from `GetActiveSessionAsync`. The lookup happens inside `TraceWriter` — `ApiClient` itself does not call `GetActiveSessionAsync` directly. `TraceWriter` fetches the active session, fills in `Session = activeSession.Name` and `SessionId = activeSession.UniqueId`, then calls `IncrementEntryCountAsync(activeSession.UniqueId)` for the seq.

A: Three new codes:
```csharp
public static readonly string SESSION_NOT_FOUND   = "SESSION_NOT_FOUND";    // exit 1 — no session with given id/name
public static readonly string SESSION_AMBIGUOUS   = "SESSION_AMBIGUOUS";    // exit 1 — --name matches multiple sessions

```
`SESSION_AMBIGUOUS` message should include the matching UUIDs: `"Multiple sessions named 'Desk-Analysis' exist. Use --id with one of: aaaa1111, bbbb2222."`
